# Guard Center 優化與實作歷程報告

這次對話的工作，表面上從數個 UI 小問題開始，最後逐步發展成一輪涵蓋介面設計、硬體控制、非同步處理、資料去重、狀態一致性與實機驗證的完整優化。核心目標始終一致：Guard Center 在瀏覽狀態下必須輕量、流暢；只有使用者真正操作功能時，才執行必要的系統或硬體工作。

## 一、UI 與操作流程整理

最初先處理 Module 列表 scrollbar 與卡片重疊，以及 Protected apps 版面不對稱等問題。Protected apps 改成收合式卡片：未展開時只顯示圖示與 App 名稱；展開後才顯示 Windows key protection、Input method protection 與 App information。兩個保護區塊採等寬配置，資訊改成一列一項，避免原本路徑、來源與狀態全部擠在一起。

Display Guard 移除了沒有實際作用的 Results 卡片，亮度與對比度旁增加 `−`、`+`，讓使用者能以 1% 為單位精確調整。Module 列表則加入拖曳排序、插入提示、自動捲動與順序持久化，並在 Modules 標題旁增加調整模式按鈕，避免一般瀏覽時誤觸拖曳。

Audio Guard 與 App Guard 中沒有實質用途的 Results／Apps 說明卡片也被移除。App Guard 原本還有第二層 scrollbar，後來統一成單一頁面捲動，使操作層級更自然。

## 二、程式邏輯正確，不代表硬體操作好用

整段開發最重要的經驗，出現在 Display Guard 的亮度控制。

最初 slider 每移動一次就立即寫入螢幕。從程式邏輯看，數值改變就套用完全正確；但實際螢幕可能透過 DDC/CI、WMI 或廠商驅動執行硬體交易。這些交易有延遲，韌體處理速度也不一致。拖曳一次可能產生數十筆寫入，硬體來不及完成上一筆，下一筆又進來，結果就是滑桿難以控制、畫面延遲，甚至讀回舊值。

第一步是改成滑鼠放開才套用，降低硬體寫入頻率。但接著出現更細微的問題：例如從 23% 拉到 26%，放開時 UI 先跳回硬體尚未更新的 23%，等寫入完成後再跳到 26%。功能最終正確，視覺卻不完整。

這反映出三種狀態不能混為一談：

- 使用者目前希望的值
- 已排入硬體寫入的值
- 硬體最後確認的值

後續讓 UI 在操作期間保留使用者的目標值，不允許較舊的硬體 readback 覆蓋畫面；硬體寫入則採序列化與 latest-value-wins 的方向處理。曾考慮 debounce，但固定 220ms 延遲會讓按鈕調整顯得遲鈍，因此最後不依賴 debounce，而是解決過期結果回寫 UI 的根本問題。快速連按 `+`、`−` 時也不再回跳，同時盡量維持低延遲。

這就是嵌入式與硬體控制常見的落差：API 呼叫成功，只代表命令送出，不代表裝置已經完成；讀到數值，也不一定代表它是最新狀態。真正可用的系統必須考慮裝置速度、命令順序、過期回應、UI thread 與實際物理反應。

## 三、從定時輪詢轉向情境式刷新

Audio Guard 與 Display Guard 原本依賴手動 Refresh，後來討論定時輪詢。最初評估每秒輪詢對 CPU 影響很小，但進一步分析後，兩者其實不應採相同策略。

Audio 的 session 可能隨程式啟動、關閉與輸出裝置切換頻繁變動，因此保留每秒一次更新，但限制在 Guard Center 視窗有效、頁面位於 Audio Guard 時執行。真正造成切換 Audio Guard 卡頓的原因，也不是每秒輪詢本身，而是進入頁面時在 UI thread 同步執行完整 Core Audio session 列舉。將列舉移出 UI thread 後，頁面切換恢復流暢。

Display 裝置拓撲相對穩定，沒有必要每秒讀取。因此改成事件導向的完整刷新，只在程式啟動、切換到 Display Guard、Guard Center 重新取得焦點且目前就在 Display Guard、顯示設定變動、睡眠恢復與手動 Refresh 時執行。這比固定輪詢更符合資料特性，也避免反覆建立實體螢幕 handle、執行 WMI 或 DDC 偵測。

## 四、App Guard 的背景載入與資料整理

App Guard 需要整合 Registry、Start Menu、Steam 與 Installed apps 等來源，完整列舉本來就可能耗時。問題不是不能掃描，而是不應阻塞 Guard Center 的頁面切換。因此改成背景載入，在 App list 顯示進度圈，使用者仍可自由切換頁面。

重複 App 則參考 Windows 原生 Installed apps 呈現方式，從「每一筆來源都顯示」改成「邏輯上同一個 App 合併」。Apex、極速快感、Docker Desktop 等項目會綜合執行檔路徑、Steam logical ID、安裝資訊與來源品質進行去重，同時優先保留較可靠的名稱、Publisher、啟動路徑與圖示。這讓列表更接近使用者理解的「有哪些應用程式」，而不是底層資料來源的原始集合。

## 五、應用程式圖示與孤兒檔案管理

Settings 新增 Application icon 功能，可選擇圖片並立即套用到 Guard Center 視窗、工作列、系統匣、捷徑、Explorer 整合及 App Guard 自身卡片。

儲存策略沒有使用 GUID 或時間戳累積圖片，而是固定管理：

- `CustomAppIcon.png`
- `CustomAppIcon.ico`

上傳第二張時直接原子覆寫第一張受管副本；Reset 則刪除兩個檔案並恢復內建圖示。原始圖片仍由使用者管理，程式不會誤刪來源檔。實際檢查確認資料夾始終只有兩個必要檔案，沒有 `.tmp`、舊版或孤兒圖片。

這段也出現一次驗證流程上的教訓：自動化工具對 Windows 原生 OpenFileDialog 的操作回報不同步，實際匯入已成功，卻因沒有立即收到視窗關閉狀態而反覆重試。後來明確區分「產品功能問題」與「驗證工具限制」，並設定停止點，避免輔助驗證反過來拖累工作。

## 六、Game Helper 的管理流程整合

Game Helper 原本有 Add apps 與 Protected apps 兩個視窗，使用者必須在兩邊切換。最後整合成單一 `Manage apps`：

- `Protected apps` 預設開啟，立即顯示現有設定，不掃描電腦。
- `All apps` 第一次切換時才在背景載入 App catalog。
- 未加入 App 只有 `Add`，完全不能展開。
- 已加入 App 顯示 `Protected ▼`，才具備展開能力。
- Protected 旁增加 `×`，可直接批次移除，不必逐張展開。
- Add 後變成 Protected，但維持收合，不強迫打開細節。
- 新加入 App 的五項保護預設全部開啟。

過程中也找到一個實際根因：候選 App ID 帶有 `exe:` 前綴，而 Protected App ID 沒有，因此同一個 App 可能仍顯示 Add。最後不再直接比較兩種 ID，而是以正規化執行檔路徑建立 Dictionary，初始化一次後以 O(1) 查詢保護狀態。

## 結語

這次優化最大的轉變，是從「功能有做出來」進一步走到「使用者操作時真的自然」。軟體資料結構、事件流程與測試全部正確，只能證明邏輯成立；碰到實體螢幕、Core Audio、Windows Registry、原生對話框與不同韌體後，還必須處理延遲、阻塞、過期狀態、裝置生命週期與使用者感知。

最終 Guard Center 不只是畫面更整齊，而是建立了一套一致原則：瀏覽時不做不必要的重工作、硬體寫入與 UI 狀態分離、昂貴列舉改成背景或情境式執行、列表以使用者理解的 App 身分呈現，所有修改則透過 Release 建置、完整測試、實際執行檔同步與可逆的 GUI 操作共同驗證。
